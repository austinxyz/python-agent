### 1. Ingest Pipeline — 端到端实现（Groups 1–9）
**提交：** `bb952c1`

**功能：**
- **JobRegistry**：threading.Lock 保护的线程安全内存 Job 注册表，支持 create / get / update
- **FileService**：`save()` 将原始文件写入 `UPLOADS_PATH/{user_id}/{file_id}/`；`register()` 写 SQLite `files` 表；路径遍历双重防护（allowlist 正则 + `is_relative_to`）
- **IngestPipeline**（LangGraph StateGraph，7 节点）：Source Router → Fetch → Clean → Chunk → Embed → Store → Summary；支持 `file` / `url` / `text` 三种 source_type
- **Flask API**：`POST /api/ingest`（202 + job_id，50 MB 限制，后台线程）；`GET /api/ingest/status/<job_id>`（UUID 格式校验，404 / 200）
- **Pinia ingest store**：destination、jobs 状态；addJob / updateJob（immutable map+spread）/ fetchJobStatus（含 error 处理）
- **IngestView.vue**：两 tab 布局（新建摄入 / 已上传文件），destination 切换，source 输入区，进度列表，文件列表 + TreeNav 过滤

**代码审查发现：**
| 级别 | 问题 | 修复 |
|------|------|------|
| CRITICAL | SSRF：字符串前缀只拦截 `172.16.x.x`，遗漏 Docker bridge `172.17–172.31` | 改用 `ipaddress.ip_network("172.16.0.0/12")` 覆盖完整 RFC 1918 |
| HIGH | `file_svc.save()` 未调用，原始文件只写元数据不落盘 | 在 `store_node` 中补 `save()` 调用 |
| HIGH | `updateJob` 使用 `Object.assign` 违反项目不可变规范 | 改为 `this.jobs.map((j, i) => i === idx ? {...j, ...patch} : j)` |
| HIGH | UUID 校验正则未覆盖测试用假 ID | 测试 ID 统一改为正规 UUID 格式，新增 `test_invalid_job_id_format_returns_400` |
| MEDIUM | `v-show` 在 happy-dom 中 `isVisible()` 误判 | 改用 `:hidden` attribute，Vue Test Utils 直接检查 `element.hidden` |

**测试：** 90 tests 全部通过（新增 64 backend + 26 frontend）

- **私有模板（6 个预设）**：`private_templates.py` 定义 `tax`/`retirement`/`portfolio`/`personal`/`real_estate`/`freeform`，每个包含 `type`/`label`/`fields`，字段含 `key`/`label`/`type`/`placeholder`；`derive_text_for_embedding()` 按模板字段顺序生成稳定的 embedding 文本
- **私有条目 API**（`backend/app/routes/private.py`）：
  - `GET /api/private/templates` — 返回 6 个模板定义
  - `GET /api/private/entries` — 列出 user_id="default" 的所有条目，按 created_at DESC 排序
  - `POST /api/private/entries` — 校验 template_type/title → 派生 embedding 文本 → embed() → upsert Qdrant point（payload 含 user_id）→ 写入 SQLite；返回 201
  - `PUT /api/private/entries/{id}` — 重新 embed 并 upsert 同 UUID 点；更新 SQLite；404 if not found for user
  - `DELETE /api/private/entries/{id}` — Qdrant `PointIdsList` 删除 + SQLite DELETE；404 if not found
- **私有笔记 API**：
  - `GET /api/private/notes` — 返回 `{notes: [...], tree: {...}}`；`_build_tree()` 按 directory 路径切分递归构建嵌套字典，每节点 `_notes` 字段持有该目录下笔记
  - `POST /api/private/notes` — title 必填、可选 directory/content/chat_ref；不写入 Qdrant
  - `PUT /api/private/notes/{id}` — 部分更新 title/directory/content；`updated_at` 自动刷新
- **QdrantService 扩展**：新增 `delete_private(point_ids)` → `PointIdsList` 删除
- **Pinia private store**（`frontend/src/stores/private.js`）：templates / entries / notes / notesTree / error 状态；fetchTemplates / fetchEntries / fetchNotes / createEntry / updateEntry / deleteEntry / createNote / updateNote actions；所有状态更新使用展开/filter/map（不可变模式）
- **PrivateView.vue**：渐变 header；上半部分 — 模板条目列表（`data-entry-card` 卡片含模板徽章、标题、摘要、编辑/删除按钮）+ 新建流程（模板选择器 → 动态字段表单 → 保存）；下半部分 — 笔记目录树（递归 `NoteTreeNode` 组件，可折叠 📁/📝 标识）+ 阅读面板（点击查看 → 编辑切换 textarea → 保存）
- **STUB_ROUTES**：`test_app_factory.py` 移除 `/api/private`

**安全性：**
- 所有 Qdrant `upsert_private` 调用 payload 包含 `user_id="default"`
- `search_private(user_id=...)` 强制要求 user_id 参数（无默认值）
- `delete_private` 仅按 ID，但路由层先在 SQLite 校验 `user_id="default"` 后才删除
- 笔记 API 完全不接触 Qdrant（V1 不做向量化）

**代码审查发现：**
| 级别 | 问题 | 修复 |
|------|------|------|
| HIGH | `create_entry` Qdrant 先于 SQLite，进程崩溃可能留下孤立向量 | 改为先 SQLite commit 再 upsert Qdrant — SQLite 是真相源，失败可重建向量 |
| HIGH | `update_entry` 同样的 Qdrant→SQLite 顺序问题；最终 SELECT 缺少 `user_id` 过滤 | 改为先 UPDATE 再 upsert；所有 SELECT 加上 `WHERE user_id = ?` 保持隔离不变量 |
| HIGH | `delete_entry` Qdrant 在 SQLite 连接 context 内调用，Qdrant 失败时 SQLite 回滚但向量已删 | 改为 SQLite DELETE 先 commit，再调用 Qdrant delete |
